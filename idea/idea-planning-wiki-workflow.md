# 아이디어 구체화 및 Wiki 축적 워크플로

## 1. 한 줄 요약

정리되지 않은 서비스·기능·업무 개선·개발 프로젝트 아이디어를 AI 기획 파트너와 대화를 통해 검증 가능한 형태로 구체화하고, 확정된 결과를 표준 Markdown 문서로 만들어 Wiki의 아이디어 백로그에 지속적으로 축적하는 워크플로다.

## 2. 배경 및 문제

아이디어는 대개 처음부터 요구사항이 정리된 상태로 등장하지 않는다. 문제의식, 기능 생각, 구현 아이디어, 운영 방식 등이 섞여 있고 중요한 정책이나 범위가 빠져 있는 경우가 많다.

이 상태에서 바로 문서화를 시작하면 다음 문제가 발생한다.

- 사용자의 원래 의도보다 문서 형식에 맞추는 것이 우선될 수 있다.
- AI가 빈칸을 임의로 채우면서 사용자가 결정하지 않은 내용이 사실처럼 굳어질 수 있다.
- MVP와 장기 비전이 섞여 초기 검증 범위가 불필요하게 커질 수 있다.
- 이후 대화에서 결정이 변경되어도 기존 결정과 충돌하거나 누락될 수 있다.
- 좋은 아이디어가 대화 안에서만 끝나고 재사용 가능한 지식으로 축적되지 않는다.

따라서 아이디어 수집, 질문, 대안 검토, 결정 관리, 문서화, Wiki 저장을 하나의 일관된 흐름으로 관리할 필요가 있다.

## 3. 목표

- 사용자의 초기 아이디어를 실제 검토·공유·설계에 활용할 수 있는 수준으로 구체화한다.
- 사용자가 직접 결정한 내용과 AI의 제안·추정을 명확히 분리한다.
- 핵심 가치 검증을 위한 MVP와 이후 확장 범위를 구분한다.
- 대화 중 확정된 결정을 유지하고 변경 시 최신 결정을 반영한다.
- 완성된 아이디어를 표준 형식으로 Wiki에 축적하여 후속 기획·설계·구현의 출발점으로 사용한다.
- 동일하거나 실질적으로 같은 아이디어가 이미 존재하는 경우 중복 생성보다 기존 문서 업데이트를 우선한다.

### 성공 기준

- 최종 문서만 읽어도 문제, 대상 사용자, 목표, 핵심 동작, MVP 범위를 이해할 수 있다.
- 중요한 미결정 사항이 결정사항처럼 기록되지 않는다.
- 이미 확정된 내용을 반복해서 질문하지 않는다.
- 최종 문서가 Wiki에서 검색·재사용 가능한 상태로 저장된다.

## 4. 대상 사용자

### 주요 사용자

아이디어를 빠르게 떠올리지만 처음부터 기획 문서 형태로 정리하기보다는 대화를 통해 발전시키고 싶은 사용자.

### 핵심 요구

- 생각나는 대로 말해도 핵심 문제와 의도를 파악해 줄 것
- 중요한 누락만 선별해 질문할 것
- 더 단순하거나 현실적인 대안이 있으면 적극적으로 제안할 것
- AI가 제안한 내용을 임의로 확정하지 않을 것
- 결정사항을 대화가 길어져도 잃지 않을 것
- 최종 결과를 다시 정리하지 않아도 Wiki에 바로 축적할 수 있을 것

## 5. 핵심 아이디어

이 워크플로는 AI를 단순 문서 작성기가 아니라 **아이디어를 검증하고 결정사항을 관리하는 기획 파트너**로 사용한다.

아이디어가 들어오면 먼저 목적·문제·사용자·기대 결과·핵심 동작을 파악한다. 방향에 영향을 주는 정보가 부족한 경우에만 질문하고, 합리적인 대안이 존재하면 AI 제안으로 제시한다.

기능이 커지기 시작하면 Vision, MVP, Later, Out of Scope로 나누어 초기 검증 범위를 보호한다. 충분한 정보가 모였거나 사용자가 문서화를 요청하면 표준 Markdown 문서로 전환하고, `$upload-wiki idea` 흐름을 통해 Wiki에 저장한다.

## 6. 주요 사용 흐름

1. 사용자가 정리되지 않은 아이디어를 자유롭게 설명한다.
2. AI가 무엇을 만들려는지, 왜 필요한지, 누가 사용하는지, 어떤 결과를 기대하는지 파악한다.
3. 필요하면 현재 내용을 `확정`, `AI 제안/추정`, `확인 필요`로 나누어 정리한다.
4. 결과에 큰 영향을 주는 미결정 사항을 우선 질문한다.
5. 더 단순한 해결책, 자동화, 운영 비용 절감, 기존 시스템 활용, 단계적 구현 가능성을 검토해 제안한다.
6. 사용자가 승인한 내용만 결정사항으로 관리한다.
7. 기능이 늘어나면 Vision / MVP / Later / Out of Scope로 범위를 분리한다.
8. 문서화 조건이 충족되면 표준 아이디어 문서로 작성한다.
9. Wiki에서 동일하거나 실질적으로 같은 아이디어가 있는지 확인한다.
10. 기존 문서가 있으면 업데이트하고, 없으면 신규 문서를 생성한다.
11. 실제 저장 결과를 확인하고 문서명, 상태, 저장 위치를 사용자에게 알린다.

## 7. 핵심 기능

### 7.1 아이디어 이해

**설명**  
초기 입력에서 목적, 문제, 사용자, 기대 결과, 기존 방식과의 차이를 파악한다.

**필요한 이유**  
표면적인 기능 요구를 그대로 문서화하면 실제 해결하려는 문제와 구현이 어긋날 수 있기 때문이다.

**우선순위**  
MVP 필수.

### 7.2 중요도 기반 질문

**설명**  
모든 빈칸을 질문하지 않고 답변에 따라 방향이 크게 달라지는 사항부터 묻는다.

주요 질문 영역:

- 핵심 사용자와 사용 목적
- 핵심 사용 흐름
- MVP 범위
- 정책과 권한
- 기존 시스템과의 관계
- 운영 방식
- 데이터 및 외부 연동
- 기술·비용·조직 제약
- 성공 판단 기준

**필요한 이유**  
질문이 많아질수록 아이디어 발전보다 인터뷰 자체가 목적이 되는 문제를 막기 위해서다.

**우선순위**  
MVP 필수.

### 7.3 AI 제안과 사용자 결정 분리

**설명**  
AI가 제시하는 개선안·대안·추정은 명시적으로 제안 상태로 유지하며, 사용자가 승인한 이후에만 결정사항으로 전환한다.

**필요한 이유**  
AI가 자연스럽게 보완한 내용이 사용자의 요구사항으로 오인되는 것을 방지한다.

**우선순위**  
MVP 필수.

### 7.4 결정 관리

**설명**  
대화에서 확정된 결정은 이후 기본 전제로 유지한다. 새로운 요구가 기존 결정과 충돌하면 충돌을 알리고 최신 사용자 결정을 반영한다.

**필요한 이유**  
긴 기획 대화에서 같은 질문이 반복되거나 서로 모순된 정책이 문서에 남는 문제를 방지한다.

**우선순위**  
MVP 필수.

### 7.5 범위 관리

**설명**  
기능이 늘어나면 다음 네 범위로 분리한다.

- Vision: 최종적으로 만들고 싶은 형태
- MVP: 핵심 가치를 검증하는 최소 범위
- Later: 가치가 있지만 초기 검증에는 필요하지 않은 기능
- Out of Scope: 현재 명시적으로 다루지 않을 범위

**필요한 이유**  
아이디어를 불필요하게 거대한 프로젝트로 만드는 것을 막고 빠른 검증을 가능하게 한다.

**우선순위**  
MVP 필수.

### 7.6 사전 검증

**설명**  
문서 확정 전 목표와 기능의 일치 여부, 사용자 흐름, 운영·권한·데이터·보안 문제, 현실적인 제약, 실패 가능성 등을 점검한다.

**필요한 이유**  
문서가 깔끔하게 정리되어 있어도 실제 실행 시 실패할 구조적 문제를 미리 발견하기 위해서다.

**우선순위**  
MVP 필수.

### 7.7 표준 문서 생성

**설명**  
완성된 아이디어는 공통 메타데이터와 정형화된 Markdown 구조로 작성한다.

기본 메타데이터:

- Status
- Version
- Created
- Updated
- Tags

기본 본문:

1. 한 줄 요약
2. 배경 및 문제
3. 목표
4. 대상 사용자
5. 핵심 아이디어
6. 주요 사용 흐름
7. 핵심 기능
8. 범위
9. 결정된 사항
10. 미결정 사항
11. 다음 작업

운영, 데이터, 기술, 제약, 위험, 단계별 구현은 필요한 경우에만 추가한다.

**우선순위**  
MVP 필수.

### 7.8 Wiki 중복 확인 및 저장

**설명**  
최종 문서 확정 후 `$upload-wiki idea` 흐름으로 동일·유사 아이디어를 먼저 확인한다. 기존 문서가 있으면 업데이트하고 없으면 신규 생성한다.

**필요한 이유**  
아이디어 백로그가 중복 문서로 분산되는 것을 막고 하나의 문서가 최신 결정사항을 유지하도록 하기 위해서다.

**우선순위**  
MVP 필수.

## 8. 범위

### MVP

- 자유 형식 아이디어 입력
- 핵심 의도 및 문제 파악
- 중요도 기반 추가 질문
- 확정 / AI 제안 / 확인 필요 구분
- 결정사항 유지 및 충돌 검토
- Vision / MVP / Later / Out of Scope 구분
- 최종 사전 검증
- 표준 Markdown 문서 생성
- Wiki 중복 확인
- 신규 문서 생성 또는 기존 문서 업데이트
- 저장 결과 확인

### Later

- 문서 상태 변경에 따른 후속 작업 자동 제안
- 아이디어 간 연관 관계 및 링크 자동 생성
- Ready 상태 아이디어에서 PRD·기술설계·Task로 이어지는 자동 워크플로
- 아이디어 백로그 우선순위 평가
- 유사 아이디어 의미 기반 자동 병합 후보 제안

### Out of Scope

- 사용자 승인 없이 중요한 제품 정책을 자동 확정하는 기능
- 모든 아이디어를 자동으로 PRD나 구현 Task까지 확장하는 기능
- 정보가 부족한 상태에서 AI 추정으로 완성 문서를 강제로 만드는 방식

## 9. 결정된 사항

- AI의 역할은 단순 요약자가 아니라 전문 기획 파트너다.
- 아이디어를 처음 듣자마자 완성 문서로 만들지 않는다.
- 중요한 정보가 부족하거나 여러 의미로 해석되는 경우 질문한다.
- 이미 답한 내용은 다시 질문하지 않는다.
- 모든 빈칸보다 방향에 영향을 주는 사항을 우선 질문한다.
- AI 제안과 사용자 결정을 구분한다.
- 사용자가 승인하지 않은 중요한 제안은 결정사항으로 취급하지 않는다.
- 기능이 늘어나면 Vision / MVP / Later / Out of Scope로 분리한다.
- 신규 아이디어 문서의 기본 상태는 `Idea`, 버전은 `0.1`이다.
- 아이디어 상태는 `Idea → Planning → Ready → In Progress → Done`을 사용하고 필요 시 `Archived`를 사용한다.
- 문서화 조건이 충족되면 표준 Markdown 문서로 전환한다.
- 사용자가 별도로 업로드하지 말라고 하지 않는 한 최종 문서는 Wiki 등록까지 진행한다.
- Wiki 등록 전 동일하거나 실질적으로 같은 문서가 있는지 확인하고, 기존 문서가 있으면 업데이트를 우선한다.
- 기존 문서 업데이트 시 Created는 유지하고 Updated를 갱신한다.
- 실제 업로드에 실패한 경우 업로드했다고 표현하지 않는다.

## 10. 미결정 사항

- 아이디어 백로그의 장기적인 디렉터리·파일명 규칙을 별도 규칙으로 더 세분화할지 여부
- 아이디어 간 우선순위나 점수 체계를 도입할지 여부
- `Planning` 또는 `Ready` 상태로 전환하기 위한 정량적 체크리스트를 둘지 여부
- 후속 산출물(PRD, UX/UI, 데이터 모델, 아키텍처 등)을 별도 자동화 워크플로로 연결할지 여부

## 11. 다음 작업

1. `idea/` 디렉터리를 Wiki의 공식 아이디어 백로그 영역으로 운영할지 확정한다.
2. `$upload-wiki idea`의 파일명·인덱스 갱신·중복 판별 규칙을 명문화한다.
3. 실제 아이디어 2~3건에 적용해 질문량, 문서 깊이, MVP 구분 품질을 검증한다.
4. 반복적으로 발생하는 누락이나 불필요한 질문 패턴을 수집해 프로젝트 지침을 개선한다.
5. 이후 필요성이 확인되면 `Ready` 상태 문서를 PRD나 구현 계획으로 넘기는 후속 워크플로를 설계한다.
