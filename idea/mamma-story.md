# 맘마스토리 (Mamma Story)

## 1. 한 줄 요약

이유식 재료를 게임의 인벤토리처럼 관리하고, 가공·제작·섭취·도감·퀘스트·커리큘럼을 연결해 부모가 "지금 무엇을 먹이고 무엇을 준비해야 하는가"를 빠르게 파악할 수 있게 하는 게임형 이유식 관리 서비스다.

1차로 실제 한 가정의 부부가 사용하는 Alpha를 만들고, 실사용 검증 후 지인 부모 대상 Beta를 거쳐 웹·Android·iOS 정식 서비스로 확장한다.

## 2. 배경 및 문제

이유식을 진행하면서 필요한 재료, 현재 냉장고 재고, 먹여본 재료, 재료 조합, 이유식 단계, 알레르기 테스트 상태 등을 한 사람이 기억하고 다른 보호자가 반복해서 물어보는 상황이 발생한다.

기존의 단순 기록 방식보다 실제 이유식 준비 과정을 `재료 → 가공 → 이유식 제작 → 먹이기`라는 흐름으로 표현하고, 이를 인벤토리·제작·퀘스트·도감 같은 익숙한 게임 문법으로 보여주면 정보를 더 직관적으로 관리할 수 있다.

핵심 문제는 기록 자체가 목적이 아니라 다음 세 가지다.

- 냉장고에 어떤 이유식 재료와 완성 이유식이 있는지 즉시 알기 어렵다.
- 무엇을 먹여봤고 무엇을 앞으로 시도해야 하는지 보호자 간 지식이 분산된다.
- 육아 중 상세한 입력을 반복해야 하는 서비스는 사용하기 어렵다.

## 3. 목표

### 제품 목표

- 보호자 간 이유식 관련 반복 질문을 줄인다.
- 냉장고의 실제 재료와 가공품, 완성 이유식을 하나의 인벤토리에서 관리한다.
- 한 번 제작 정보를 입력하면 실제 식사 기록은 가능한 한 원클릭으로 끝낸다.
- 아기가 경험한 재료, 선호도, 반응, 커리큘럼 진행 상황을 자동으로 축적한다.
- 이유식 커리큘럼 및 알레르기 기준을 앱 로직과 분리해 검증된 조사 데이터를 추후 주입할 수 있게 한다.

### Alpha 성공 판단 기준

정량 기준은 Alpha 사용 후 확정한다. 우선 다음을 관찰한다.

- 부부가 실제 일상에서 지속적으로 사용하는가.
- 이유식 관련해서 서로 확인해야 하는 횟수가 감소하는가.
- 일반적인 섭취 기록을 몇 번의 탭만으로 완료할 수 있는가.
- 앱의 재고와 실제 냉장고 재고가 과도하게 어긋나지 않는가.
- 제작·도감·퀘스트 구조가 실제 이유식 준비 흐름과 맞는가.

## 4. 대상 사용자

### Alpha

이유식을 먹이는 한 가정의 보호자 2명. 동일한 아이 프로필과 데이터를 공유한다.

### Beta

주변의 이유식 단계 아이를 둔 부모 가정. 가정마다 다른 이유식 준비 방식에서도 시스템이 유효한지 검증한다.

### Release

이유식 재료·섭취·진행 상황을 공동 관리하고 싶은 일반 보호자.

## 5. 핵심 아이디어

맘마스토리는 이유식 관리를 게임의 성장 및 아이템 시스템으로 표현한다. 단, 중세 RPG 분위기나 전투 요소를 사용하는 것이 아니라 아기가 주인공인 밝고 귀여운 게임 경험을 지향한다.

메이플스토리 세대의 부모에게 익숙한 `인벤토리`, `제작`, `퀘스트`, `도감`, `챕터` 등의 문법에서 영감을 얻되 특정 게임의 캐릭터·그래픽·아이콘 등 IP를 복제하지 않는다.

핵심 구조는 다음과 같다.

`스토리/커리큘럼 → 인벤토리 → 가공/제작 → 이유식 아이템 → 섭취 → 도감/선호도/퀘스트 갱신`

### 주요 용어

- **인벤토리**: 실제 냉장고의 이유식 관련 아이템을 관리하는 공간
- **재료 아이템**: 구매하거나 보유한 원재료
- **가공 아이템**: 손질·조리·소분하여 부모가 만든 중간 아이템
- **이유식 아이템**: 재료 아이템과 가공 아이템을 조합해 만든 최종 섭취 대상
- **스토리**: 이유식 단계와 Chapter로 구성된 전체 커리큘럼
- **퀘스트**: 현재 단계에서 수행할 커리큘럼 목표 및 알레르기 테스트
- **도감**: 지금까지 경험한 재료와 반응·선호도 이력
- **업적**: 재미를 위한 수집/달성 요소. MVP에서는 제외

## 6. 주요 사용 흐름

### 6.1 최초 시작

1. 아이 프로필을 등록한다.
2. 이유식을 처음 시작하는지, 이미 진행 중인지 선택한다.
3. 현재 이유식 단계와 Chapter를 선택한다.
4. 이미 진행 중이라면 먹어본 재료를 빠르게 다중 선택할 수 있다.
5. 과거 기록 입력이 번거롭다면 `오늘부터 기록`으로 건너뛸 수 있다.
6. 현재 냉장고의 재료 및 가공품을 인벤토리에 등록한다.

과거 데이터가 없는 경우 `미경험`과 `기록 없음`은 서로 다른 상태로 취급한다.

### 6.2 재료 가공

1. 인벤토리의 재료 아이템을 선택한다.
2. 가공 방법과 결과 수량/단위를 입력한다.
3. 원재료가 차감된다.
4. 사용자가 정의한 가공 아이템이 생성된다.

예: `닭고기 300g → 닭고기 큐브 15g × 20`

### 6.3 이유식 제작

1. 재료 아이템과 가공 아이템을 선택한다.
2. 사용량과 제작 수량을 입력한다.
3. 사용한 아이템이 인벤토리에서 차감된다.
4. 구성 재료와 양을 포함한 이유식 아이템이 생성된다.

예: `쌀죽 베이스 + 소고기 큐브 + 애호박 큐브 + 당근 → 소고기 채소죽 × 3`

즉석 조리도 동일한 제작 모델을 사용하되, 제작 후 바로 섭취 흐름으로 이동할 수 있게 한다.

### 6.4 섭취 기록

이유식 아이템에는 구성 재료와 양이 이미 정의되어 있으므로 실제 식사 시 상세 재료를 다시 입력하지 않는다.

기본 선택지는 다음 세 가지다.

- 다 먹음
- 좀 남김
- 안 먹음

`다 먹음`과 `안 먹음`은 선택 즉시 기록을 완료한다. `좀 남김`을 선택한 경우에만 남긴 비율을 추가로 기록한다.

시스템은 이유식 레시피와 남긴 비율을 이용해 각 재료의 추정 섭취량을 계산하고 식사 이력, 도감, 관련 퀘스트에 반영한다.

### 6.5 재고 보정 및 폐기

현실의 재고와 앱 데이터가 달라질 수 있으므로 재료·가공·이유식 아이템 모두 빠르게 수량을 보정하거나 폐기할 수 있다. 이유 입력은 강제하지 않는다.

## 7. 핵심 기능

### 7.1 인벤토리

재료, 가공품, 이유식을 동일한 인벤토리 개념 아래 관리한다.

기본 입력은 `소고기 큐브 ×4`처럼 간단하게 유지하고 필요할 때만 중량, 냉장/냉동 상태, 제조일, 소비기한 등의 상세 정보를 기록하는 혼합형 방식을 사용한다.

### 7.2 가공 및 제작

가공 아이템은 정해진 목록만 사용하는 것이 아니라 부모가 원재료를 가공하면서 직접 생성할 수 있다. 이유식은 재료 아이템과 가공 아이템을 자유롭게 조합해 제작한다.

제작 시 레시피를 저장하여 이후 섭취 기록에서 재료 정보를 다시 입력하지 않도록 한다.

### 7.3 간편 섭취 기록

평소 기록은 최소한의 탭으로 끝내는 것을 UX 최우선 원칙으로 한다. 상세 입력은 기본 흐름에서 숨기고 필요한 상황에서만 노출한다.

**제품 원칙: 부모는 무엇을 만들었는지 한 번만 입력하고, 이후에는 결과만 기록한다.**

### 7.4 도감 및 선호도

재고와 경험 데이터를 분리한다. 재고가 0이 되어도 과거 섭취 경험은 도감에 남는다.

재료별로 최소 다음 세 축을 관리한다.

- 경험 상태: 기록 없음 / 미경험 / 경험함 / 섭취 이력
- 반응 상태: 미확인 / 테스트 중 / 특이 반응 기록 없음 / 반응 기록 있음 등
- 선호 상태: 좋아함 / 보통 / 싫어함

섭취 결과만으로 특정 재료의 선호도를 단정하지 않는다. 여러 식사에서 특정 재료가 포함된 이유식의 거부 패턴이 반복될 경우 시스템이 보호자에게 선호도 확인을 제안하는 방식이 적합하다.

또한 `추천 허용 / 잠시 제외 / 제외`와 같이 추천 여부를 선호도와 별도로 관리할 수 있어야 한다.

### 7.5 스토리/커리큘럼

`초기 → 중기 → 후기 → 완료기` 같은 실제 이유식 단계를 상위 Stage로 두고 각 단계 아래 Chapter를 구성한다.

화면에서는 게임식 표현을 사용할 수 있지만 실제 이유식 단계 정보를 함께 표시한다.

Chapter에는 향후 조사된 기준 데이터를 바탕으로 식재료 경험, 식감, 식품군, 알레르기 테스트 등 진행 목표를 연결할 수 있다. 조건을 충족했다고 자동 승급하지 않고 다음 Chapter 이동 가능 상태를 안내한 뒤 보호자가 직접 이동한다. 보호자는 현재 위치를 앞뒤로 조정할 수 있다.

### 7.6 퀘스트

퀘스트는 두 종류로 구분한다.

- **커리큘럼 퀘스트**: 현재 Chapter에서 필요한 식재료·식감·경험 목표
- **알레르기 퀘스트**: 검증된 외부 기준 데이터에 따라 생성되는 중요 퀘스트

이유식 섭취 시 구성 재료를 분석하여 관련 퀘스트 진행도를 자동 반영한다. 알레르기 테스트의 구체적인 횟수·도입 시점·판정 규칙은 현재 문서에서 임의로 결정하지 않는다.

### 7.7 보호자 공동 사용

데이터의 중심은 계정이 아니라 아이 프로필이다. 하나의 아이 프로필에 기본 보호자 2계정을 연결하고 동일한 인벤토리·제작·섭취·도감·커리큘럼·퀘스트를 공유한다.

누가 어떤 작업을 수행했는지는 이력으로 남기되 일상 화면에서 과도하게 강조하지 않는다.

향후 3명 이상의 보호자를 연결할 수 있도록 관계 구조 자체는 확장 가능하게 설계한다.

## 9. UX/UI 방향

- 모바일 웹을 최우선으로 설계하되 PC에서도 모든 기능을 사용할 수 있어야 한다.
- 이유식을 먹이는 중 한 손으로 조작하는 상황을 핵심 사용 환경으로 본다.
- 상세 폼 입력보다 아이템 선택, 빠른 수량 조정, 원클릭 결과 기록을 우선한다.
- 홈 화면에서 현재 스토리 진행, 진행 중 퀘스트, 먹을 수 있는 이유식, 주요 인벤토리를 빠르게 확인한다.
- 게임화는 장식이 아니라 복잡한 정보를 빠르게 이해하고 입력을 줄이는 UX 수단으로 사용한다.
- 중세 판타지 느낌은 배제한다.
- 밝고 귀엽고 아기 중심의 분위기를 사용한다.
- 메이플스토리를 경험한 부모 세대에게 익숙한 게임 문법과 정서를 참고하되 독립적인 비주얼 아이덴티티를 만든다.

## 10. 데이터 및 연동

의학·영양 기준을 애플리케이션 코드에 하드코딩하지 않는다.

다음과 같이 앱 로직과 기준 데이터를 분리한다.

`기준 데이터 → 커리큘럼/퀘스트 생성 규칙 → 실제 섭취 기록 → 진행 상태 판정 → 도감 반영`

향후 기준 데이터에는 필요에 따라 다음 정보가 포함될 수 있다.

- 기준 출처 및 기준일
- 이유식 단계/Chapter
- 권장 식품군 및 재료
- 식감/형태 관련 정보
- 알레르기 관련 식품
- 권장 도입 조건
- 반복/관찰 조건
- 주의사항

구체적인 내용과 규칙은 별도 조사 후 확정한다.

## 11. 기술적 고려사항

- Alpha는 웹으로 시작하지만 웹 전용 도메인 구조로 만들지 않는다.
- 향후 Android/iOS 클라이언트가 동일 데이터를 사용할 수 있도록 백엔드/API와 클라이언트 책임을 분리하는 구조를 전제로 한다.
- `User ↔ Child` 관계는 향후 보호자 수 확장을 고려해 N:M 관계로 표현하고 무료 보호자 수 제한은 정책 계층에서 다루는 것이 적합하다.
- 재료, 가공 아이템, 이유식 아이템 사이의 원재료/제작 관계를 추적할 수 있어야 한다.
- 이유식 레시피는 섭취 시점의 재료별 추정 섭취량을 계산할 수 있도록 스냅샷 형태로 보존할 필요가 있다.
- 구체적인 기술 스택과 Android/iOS 구현 방식은 아직 결정하지 않는다.

## 12. 단계별 구현

### Phase 1 — Alpha

실제 한 가정의 부부 2명이 매일 사용한다. 기능의 양보다 실제 사용성과 기록 마찰을 검증한다. 사용하면서 발견되는 문제를 반복 개선한다.

### Phase 2 — Beta

주변의 아이 부모에게 제공한다. 다른 가정의 이유식 방식에서도 모델이 통하는지, 설명 없이 온보딩과 핵심 흐름을 사용할 수 있는지 검증한다.

### Phase 3 — Release

범용 서비스로 정식 출시한다. 웹뿐 아니라 Android와 iOS 애플리케이션을 제공한다. 보호자 기본 2계정 정책을 유지하면서 3명 이상 연결 등 확장 기능의 과금 여부를 검토한다.

## 13. 위험 요소 및 대응

### 기록 피로

재료와 재고를 지나치게 상세히 관리하도록 요구하면 사용을 중단할 가능성이 높다. 기본 입력은 단순하게 하고 상세 데이터는 선택적으로 입력한다.

### 현실 재고와 데이터 불일치

자동 차감만으로는 실제 냉장고와 어긋날 수 있다. 빠른 재고 보정과 폐기 기능을 제공한다.

### 특정 가정 방식에 과적합

Alpha가 한 가정에서 진행되므로 해당 가정의 큐브 중심 방식에 최적화될 수 있다. Beta에서 다른 조리·소분 방식을 사용하는 가정을 통해 반드시 검증한다.

### 건강 정보의 신뢰성

알레르기 및 이유식 커리큘럼을 임의 규칙으로 구현하면 위험하다. 기준 데이터 조사를 별도 과제로 분리하고 출처와 기준일을 포함한 검증된 데이터를 주입하는 구조를 사용한다.

### 게임화가 사용성을 해칠 가능성

연출이나 용어가 핵심 정보를 가리면 안 된다. 게임 요소는 정보 파악과 입력 단축에 도움이 되는 경우에만 사용한다.

## 14. 결정된 사항

- 프로젝트명은 **맘마스토리(Mamma Story)**다.
- 가족용 Alpha → 지인 부모 Beta → 정식 Release 순으로 진행한다.
- Alpha는 실제 부부 2명만 사용한다.
- 모바일 웹 중심으로 시작하되 PC에서도 사용할 수 있어야 한다.
- Release 단계에서는 Android와 iOS 애플리케이션을 모두 제공한다.
- 아이 한 명에 보호자 2계정을 기본 연결한다.
- 3명 이상 보호자 연결은 향후 유료화 후보로 두되 Alpha에서 결제를 구현하지 않는다.
- 인벤토리는 재료 / 가공 / 이유식 아이템을 관리한다.
- 가공 아이템은 사용자가 직접 생성할 수 있다.
- 이유식은 재료 아이템과 가공 아이템을 혼합해 제작한다.
- 섭취 기록은 `다 먹음 / 좀 남김 / 안 먹음`을 기본으로 하며 `좀 남김`일 때만 남긴 비율을 추가 입력한다.
- 재고 수동 보정과 폐기를 지원한다.
- 재료 경험, 반응, 선호도를 도감에 누적한다.
- 선호도와 추천 제외 여부를 분리한다.
- 커리큘럼은 단계 + Chapter 구조이며 보호자가 현재 위치를 조정할 수 있다.
- 일반 진행은 커리큘럼 퀘스트, 알레르기 관련 진행은 중요 퀘스트로 구분한다.
- 재미 중심의 업적은 MVP에서 제외한다.
- 이유식/알레르기 기준 데이터 조사는 별도 과제로 진행한다.
- 게임 컨셉은 귀엽고 아기 중심으로 하며 중세 판타지 분위기는 사용하지 않는다.

## 15. 미결정 사항

- 실제 Stage/Chapter별 커리큘럼 내용
- 알레르기 대상 식품 및 테스트 진행 규칙
- 기준 데이터의 공신력 있는 출처와 업데이트 정책
- 재료 기본 데이터셋과 분류 체계
- Alpha의 구체적인 정량 성공 기준
- 기술 스택 및 배포 환경
- Android/iOS 구현 기술
- Beta 초대 및 계정 생성 방식
- 정식 서비스의 요금제와 3명 이상 보호자 과금 정책
- 정식 서비스에서 제공할 AI 추천 범위
