# BeScore Reboot

## 1. 한 줄 요약

과거 스포츠 정보 앱 **BeScore(비스코어)**의 경기 조회 경험을 현대적인 반응형 웹 서비스로 재구현한다. 기존 서비스의 분석·예측 기능은 제외하고, 사용자가 경기 일정·상태·스코어·주요 이벤트 등 객관적인 경기 정보를 빠르게 확인하는 데 집중한다.

## 2. 배경 및 문제

과거 BeScore는 실시간 경기 정보와 경기별 분석/예측 정보를 함께 제공하던 스포츠 애플리케이션이었다. 현재는 서비스가 종료되어 해당 사용 경험을 그대로 이용할 수 없다.

이번 아이디어는 BeScore에서 유용했던 **경기 탐색 → 경기 상태 확인 → 상세 경기 정보 확인** 흐름을 다시 살리되, 과거 앱을 그대로 복제하는 것이 아니라 웹 환경에 맞게 재구성하는 것을 목표로 한다.

이번 프로젝트에서는 분석 기능을 의도적으로 분리한다. 전문가 분석, AI 분석, 예상 스코어, 승패 예측, 베팅 추천 등을 제공하는 서비스가 아니라 **라이브스코어 및 스포츠 경기 정보 서비스**로 범위를 명확하게 제한한다.

## 3. 목표

- 사용자가 접속 즉시 오늘의 경기 일정을 확인할 수 있게 한다.
- 날짜를 변경하여 과거 경기 결과와 예정 경기를 쉽게 탐색할 수 있게 한다.
- 진행 중인 경기의 현재 상태와 스코어를 빠르게 인지할 수 있게 한다.
- 경기 상세 화면에서 주요 경기 정보와 이벤트를 확인할 수 있게 한다.
- 모바일을 중심으로 하되 PC에서도 자연스럽게 사용할 수 있는 반응형 웹으로 제공한다.
- 향후 실제 스포츠 데이터 공급자를 연결할 수 있는 확장 가능한 기반을 마련한다.

### 초기 성공 기준 제안

> 아래 항목은 아직 사용자 확정 전인 AI 제안이다.

- `사이트 접속 → 오늘 경기 확인 → 날짜 변경 → 경기 선택 → 경기 상세 확인` 흐름이 중단 없이 동작한다.
- 모바일과 데스크톱 모두에서 핵심 정보가 별도 확대 없이 읽힌다.
- 진행 중/예정/종료 상태를 경기 카드만 보고 즉시 구분할 수 있다.
- Mock 데이터 공급자에서 실제 데이터 공급자로 교체할 때 화면 로직의 대규모 수정이 필요하지 않다.

## 4. 대상 사용자

### 초기 가정

- 원하는 날짜의 스포츠 경기 일정과 결과를 빠르게 확인하려는 사용자
- 진행 중인 경기의 현재 스코어와 경기 상황을 확인하려는 스포츠 팬
- 특정 팀이나 리그의 최근/예정 경기를 반복적으로 확인하는 사용자

대상 사용자 범위와 우선순위는 아직 최종 확정하지 않았다.

## 5. 핵심 아이디어

BeScore Reboot의 중심은 **날짜 기반 경기 탐색**이다.

사용자가 사이트에 접속하면 오늘 경기를 먼저 보여주고, 각 경기를 리그 단위로 묶어 제공한다. 경기 카드에서는 팀, 시작 시간, 현재 스코어와 상태를 한눈에 보여준다. 더 자세한 정보가 필요한 경우 경기 상세 화면으로 이동하여 경기 기본 정보와 주요 이벤트를 확인한다.

분석 콘텐츠를 제거함으로써 서비스 구조와 화면 우선순위를 객관적인 경기 데이터에 집중시킨다.

## 6. 주요 사용 흐름

1. 사용자가 BeScore Reboot 웹사이트에 접속한다.
2. 오늘 날짜의 경기 목록을 확인한다.
3. 필요하면 이전/다음 날짜 또는 특정 날짜를 선택한다.
4. 리그별로 그룹화된 경기 목록에서 원하는 경기를 찾는다.
5. 경기 카드에서 시작 시간, 진행 상태, 팀과 스코어를 확인한다.
6. 경기 카드를 선택한다.
7. 경기 상세 화면에서 대회, 라운드, 경기장, 스코어와 주요 이벤트를 확인한다.
8. 진행 중인 경기라면 갱신된 경기 상태와 스코어를 계속 확인한다.

### AI 제안 흐름

- 팀/리그 검색을 통한 경기 접근
- 즐겨찾기한 팀/리그의 경기 우선 노출
- 리그/팀 상세 페이지에서 예정 경기와 최근 결과 탐색

## 7. 핵심 기능

### 7.1 날짜별 경기 목록

**설명**  
오늘을 기본값으로 날짜별 경기를 조회한다.

**필요한 이유**  
라이브스코어 서비스의 핵심 진입점이며, 예정 경기와 과거 결과를 동일한 탐색 방식으로 제공할 수 있다.

**주요 정보**

- 날짜
- 리그
- 경기 시작 시간
- 홈/원정 팀
- 팀 로고
- 스코어
- 경기 상태

**우선순위:** MVP

### 7.2 리그별 그룹화

**설명**  
같은 날짜의 경기를 리그 또는 대회 단위로 묶는다.

**필요한 이유**  
하루 경기 수가 많아져도 사용자가 원하는 경기를 빠르게 찾을 수 있다.

**우선순위:** MVP

### 7.3 경기 상태 표시

**지원 상태 후보**

- 예정
- 진행 중
- 하프타임
- 종료
- 연기
- 취소

진행 중인 경기에서는 가능한 경우 현재 경기 시간도 함께 표시한다.

예: `32'`, `HT`, `78'`, `FT`

**우선순위:** MVP

### 7.4 경기 상세

경기 상세 화면에서 데이터가 존재하는 항목을 제공한다.

- 홈/원정 팀
- 팀 로고
- 현재/최종 스코어
- 경기 상태
- 시작 시간
- 대회/리그
- 라운드
- 경기장

**우선순위:** MVP

### 7.5 주요 경기 이벤트

경기 데이터 공급자가 제공하는 경우 시간순으로 주요 이벤트를 표시한다.

- 골
- 자책골
- 페널티골
- 페널티 실패
- 옐로카드
- 레드카드
- 선수 교체

홈팀과 원정팀 이벤트는 시각적으로 쉽게 구분할 수 있도록 한다.

**우선순위:** MVP 후보 — 실제 데이터 공급 범위에 따라 조정 필요

### 7.6 경기 정보 자동 갱신

진행 중인 경기만 비교적 짧은 주기로 데이터를 갱신하고, 예정/종료 경기는 불필요하게 자주 조회하지 않는다.

구현 방식은 아직 확정하지 않는다.

**AI 제안:** MVP에서는 WebSocket보다 polling을 우선 검토한다.

### 7.7 검색

팀명 또는 리그명으로 관련 정보를 찾는다.

**상태:** AI 제안

### 7.8 즐겨찾기

관심 팀이나 리그를 저장하고 관련 경기를 쉽게 찾는다.

**AI 제안:** 초기에는 계정 시스템 없이 LocalStorage 기반으로 구현할 수 있다.

**상태:** AI 제안

### 7.9 리그/팀 상세

리그 또는 팀을 기준으로 예정 경기와 최근 결과를 탐색한다.

**상태:** AI 제안

## 8. 범위

### MVP

현재 확정된 핵심 방향을 기준으로 최소 범위는 다음과 같다.

- 반응형 웹 서비스
- 오늘의 경기
- 날짜 변경 및 날짜별 경기 조회
- 리그별 경기 그룹
- 경기 카드
- 경기 상태 및 스코어
- 경기 상세
- 실제 데이터 연동을 고려한 데이터 계층 분리

경기 이벤트는 데이터 공급 가능 범위를 확인한 뒤 MVP 포함 여부를 최종 결정한다.

### Later

아래는 현재 AI 제안이며 사용자 결정 전이다.

- 팀/리그 검색
- 즐겨찾기
- 리그 상세
- 팀 상세
- 시즌 필터
- 축구 외 스포츠 확대
- 사용자 계정 및 즐겨찾기 동기화
- SSE/WebSocket 기반 실시간 갱신
- 배당 정보 표시

### Out of Scope

현재 다음 기능은 명시적으로 제외한다.

- 전문가 경기 분석
- AI 경기 분석
- 분석 게시글
- 전문가 코멘트
- 승/무/패 예상
- 예상 스코어
- 승률 예측
- 경기 추천
- 베팅 추천
- Value 분석

현재 프로젝트의 역할은 **객관적인 경기 정보 제공**이다.

## 9. 결정된 사항

- 프로젝트명은 **BeScore Reboot**로 한다.
- 과거 BeScore의 핵심 경기 정보 조회 경험을 재현한다.
- 네이티브 앱이 아닌 **웹 서비스**로 제공한다.
- 분석 및 예측 기능은 제외한다.
- 라이브스코어와 객관적인 경기 정보 확인이 서비스의 중심이다.

## 10. 미결정 사항

- MVP에서 우선 지원할 스포츠 범위
- 축구 우선으로 시작할지, 초기부터 복수 종목을 지원할지
- 초기 지원 리그/대회 목록
- 사용할 실제 스포츠 데이터 API 또는 데이터 수집 방식
- 경기 이벤트를 MVP 필수 기능으로 포함할지
- 리그/팀 상세, 검색, 즐겨찾기의 MVP 포함 여부
- 로그인/사용자 계정 필요 여부
- 실제 경기 데이터 갱신 주기와 실시간 처리 방식
- 배당 정보를 장기적으로 서비스 범위에 포함할지
- 최종 기술 스택 및 배포 환경
- 서비스 공개 범위와 운영 비용 허용 수준

## 11. 데이터 및 연동

외부 스포츠 API는 아직 결정하지 않는다.

### AI 제안

특정 공급자에 화면과 도메인 모델이 직접 종속되지 않도록 데이터 공급 계층을 추상화한다.

예시 인터페이스:

- `GetLeagues`
- `GetMatchesByDate`
- `GetMatch`
- `GetMatchEvents`
- `GetTeam`
- `GetTeamMatches`

외부 API 응답 모델과 서비스 내부 모델도 직접 동일하게 사용하기보다 다음 흐름을 권장한다.

`External API DTO → Mapping → Domain Model → Application/UI`

실제 API가 결정되기 전에는 Mock Provider를 활용해 전체 UX를 먼저 구현할 수 있다.

Mock 데이터에는 다음 상황을 포함하는 것이 좋다.

- 예정 경기
- 진행 중 경기
- 종료 경기
- 연기/취소 경기
- 다양한 경기 이벤트

## 12. 기술적 고려사항

아래는 구현 방향에 대한 AI 제안이며 확정된 기술 스택이 아니다.

- 모바일 우선 반응형 웹
- TypeScript 기반 프론트엔드/서버 구조 검토
- 스포츠 데이터 Provider와 UI 분리
- 진행 중 경기만 선택적으로 빠른 갱신
- API 호출 제한 및 캐싱 고려
- 외부 API 장애 시 오류/부분 데이터 처리
- 서버/클라이언트 시간대를 명확히 처리
- 대한민국 사용자 기준 표시 시간 정책 검토
- 실제 서비스 공개 시 데이터 API 라이선스와 재배포 권한 확인

## 13. 위험 요소 및 대응

### 외부 데이터 품질 및 비용

스포츠 API마다 지원 리그, 라이브 갱신 주기, 이벤트 상세도와 비용 차이가 크다.

**대응 방향:** UI 구현 전에 실제 데이터 공급 후보를 비교하고 MVP가 필요로 하는 데이터 필드를 충족하는지 검증한다.

### 과도한 초기 범위

종목, 리그, 팀 페이지, 검색, 즐겨찾기, 실시간 기능을 모두 초기 구현하면 핵심 가치 검증보다 플랫폼 구축 비용이 커질 수 있다.

**대응 방향:** 우선 날짜별 경기 목록과 경기 상세 흐름을 완성한 뒤 확장 기능을 추가한다.

### 원본 서비스와의 혼동

과거 BeScore의 이름과 경험을 참고하는 만큼 원 서비스의 브랜드·디자인·콘텐츠를 그대로 복제하면 권리 관계 문제가 발생할 수 있다.

**대응 방향:** 기능적 컨셉은 참고하되 UI 디자인, 로고, 콘텐츠는 새로 제작하고 서비스 공개 전 명칭/상표 사용 가능 여부를 별도로 확인한다.

### 라이브 데이터 갱신 부하

모든 경기를 같은 주기로 갱신하면 API 호출 비용과 서버 부하가 증가한다.

**대응 방향:** 진행 중 경기와 그 외 경기에 서로 다른 갱신 정책을 적용한다.

## 14. 다음 작업

1. MVP 지원 스포츠와 리그 범위를 결정한다.
2. 후보 스포츠 데이터 API의 지원 범위, 라이브 지연, 이벤트 데이터, 가격과 라이선스를 비교한다.
3. 홈 경기 목록과 경기 상세 중심의 모바일 UX를 설계한다.
4. 기술 스택과 배포 환경을 결정한다.
5. Mock Provider 기반 Prototype을 구현한다.
6. 실제 데이터 Provider를 연결하고 갱신/캐시 정책을 검증한다.
7. 검색·즐겨찾기·리그/팀 상세의 MVP 포함 여부를 사용성 기준으로 재검토한다.
8. 공개 서비스로 전환하기 전에 BeScore 명칭 및 스포츠 데이터 재사용 관련 권리 관계를 확인한다.
