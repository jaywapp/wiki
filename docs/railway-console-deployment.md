# Railway HTTPS 콘솔을 통한 SQLite 배포 확인

확인일: 2026-11-02 · orchestrator: Codex

Railway의 인증된 웹 대시보드 Console에서 유지보수·백업을 수행하고, CLI로 새 런타임을 배포한 운영 사례다. 아래 내용은 당시 환경에서 확인한 절차이며, 요금제별 기능을 보장하는 안내는 아니다. 명령과 UID는 사용하는 애플리케이션에 맞춰 확인한다.

## 콘솔 접근과 실행 권한

SSH 호스트 키의 신뢰 근거를 확보하지 못했다면 호스트 검증을 끄거나 확인되지 않은 키를 등록하지 않는다. 이번 환경에서는 공식 HTTPS Console로 필요한 작업을 마칠 수 있었다. 이 방법으로 네이티브 SSH 접속이나 포트 터널까지 검증한 것은 아니다.

웹 콘솔은 root로 열렸다. 파일 소유권이 달라지지 않도록 애플리케이션 프로세스의 UID/GID를 확인하고 해당 계정으로 실행했다. 아래는 UID/GID가 모두 1000이고 `setpriv`가 설치된 이미지의 예다.

```sh
id
setpriv --reuid=1000 --regid=1000 --clear-groups --no-new-privs sh
id
```

새 배포 인스턴스에 다시 연결했을 때도 권한을 재확인한다. 콘솔 명령 입력과 출력 완료는 별개이므로, 다음 단계 전에 실제 성공 출력을 확인한다.

## 배포 순서와 데이터 보존

1. 배포할 소스와 커밋을 비교하고 빌드·테스트를 완료한다. 업로드 목록에서 환경 파일, DB, 키, 임시 로그를 제외한다.
2. 애플리케이션이 제공하는 유지보수 모드로 쓰기를 멈춘다.
3. SQLite 백업 API를 사용하는 프로젝트 백업 명령으로 별도 파일을 만들고 무결성·복원 가능성을 검사한다. WAL 모드에서 실행 중인 DB 본체만 복사해서 백업으로 간주하지 않는다.
4. 프로젝트의 재시작 준비 절차를 마친 뒤 새 런타임을 배포한다. 유지보수와 재시작 명령은 Railway 공통 명령이 아니라 해당 애플리케이션의 기능이다.
5. 배포 성공과 readiness HTTP 200을 확인한다. 백업과 운영 DB를 읽기 전용으로 열고, 비교 중 쓰기가 없도록 통제한 상태에서 스키마와 테이블 데이터를 비교한다. 행 정렬 기준을 명시하고 원본 데이터 대신 일치 여부만 기록한다.
6. 기존 사용자 브라우저를 새로고침해 진행 상태가 유지되는지 확인한다. 검증을 위해 불필요한 게임 진행이나 정식 도전 기록을 만들지 않는다.

같은 볼륨에 있는 검증된 백업은 배포 복구에 도움이 되지만 볼륨 자체의 손실을 대비하는 별도 보관본은 아니다. 사용자 데이터·세션 정보가 포함된 백업을 내려받을 때는 대상 파일과 보관 위치에 대한 권한을 확인한다. 백업과 비교용 원본 데이터를 Git에 올리지 않는다.

## HTTP와 성능 결과 해석

실제 HTTPS GET으로 배포 자산이 빌드 산출물과 같은지, 압축이 적용되는지, ETag 조건부 요청이 304와 빈 본문으로 응답하는지 확인한다. HEAD 응답만으로 GET의 압축 전송 여부를 결론 내리지 않는다.

로컬 처리 시간, 전송 크기, 운영 접속 시간을 구분한다. 플랫폼이 이미 압축하던 자산은 애플리케이션 압축 추가만으로 같은 비율의 운영 개선이 생기지 않는다. 첫 요청과 후속 요청의 지연 차이는 별도로 기록하고, 원인 검증 없이 자동 절전 때문이라고 단정하지 않는다.
