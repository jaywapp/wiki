# Supabase Auth Admin 계정과 기존 프로필을 안전하게 연결하기

기존 회원 명부에 Auth 계정을 발급하는 서비스에서는 계정 생성과 회원 연결의 신뢰 경계를 분리해야 한다. 사용자 metadata에 들어온 회원 ID만으로 연결하면 다른 회원의 권한을 가져갈 수 있다. 서버에서 승인한 표식과 미연결 프로필의 상태를 함께 검증해야 한다.

확인일: 2026-10-05. 이 글은 전화번호를 사용하는 기존 명부에 서버가 계정을 발급하는 패턴을 다룬다. 아래 순서는 확인한 Supabase Auth 구현의 동작이며, 영구적인 API 순서 보장은 아니다. 업그레이드 시 배포 버전의 구현과 회귀 검사를 다시 확인한다.

## createUser에 표식을 넣어도 INSERT 시점에는 없을 수 있다

확인한 Auth Admin 구현은 기본 provider metadata를 구성한 뒤, 한 트랜잭션에서 사용자를 INSERT하고 나중에 요청의 `app_metadata`를 UPDATE한다. 따라서 `AFTER INSERT` 트리거가 요청의 서버 표식을 반드시 볼 것이라고 가정하면 정상적인 계정 발급도 실패한다. [공식 Auth 구현의 생성 순서](https://github.com/supabase/auth/blob/master/internal/api/admin.go#L455-L521)

```text
Trusted provisioning endpoint
  -> authorize operator and target
  -> auth.admin.createUser({ user_metadata, app_metadata })
     -> INSERT auth.users with default provider metadata
     -> INSERT trigger: no provisioning marker, leave unlinked
     -> UPDATE auth.users.raw_app_meta_data with server marker
     -> UPDATE trigger: validate and link exactly one profile
  -> verify the resulting profile-to-auth link
```

두 저장은 별도의 클라이언트 요청을 요구하는 단계가 아니다. INSERT에서 표식 누락을 무조건 예외로 처리하는 대신 연결을 보류하고, 표식이 반영되는 UPDATE에서 검증한다. 표식이 처음부터 있는 런타임에 대비해 INSERT와 UPDATE가 같은 검증 함수를 사용할 수 있다.

## 신뢰할 값과 참고할 값

| 값 | 용도 | 연결 권한의 근거인가 |
| --- | --- | --- |
| 요청 본문의 대상 ID | 서버가 다시 조회할 대상 선택 | 단독으로는 아님 |
| `user_metadata.profile_id` | 서버 표식과 대조하는 보조 데이터 | 아님 |
| `app_metadata.profile_provisioning_id` | 인가된 서버가 선택한 연결 대상 | 서버 쓰기 경계를 보장할 때 사용 |
| 프로필의 현재 연결·연락처·권한 | 대상의 실제 상태 검증 | DB의 최신 값으로 검증 |

사용자는 `user_metadata`를 수정할 수 있으므로 RLS나 인가 판단에 사용하면 안 된다. 표시 이름, 요청 대상 ID, 사용자 입력 전화번호를 조합해도 권한 증명이 되지는 않는다. [공식 사용자 속성 안내](https://supabase.com/docs/guides/auth/users)

`auth.admin.createUser`는 신뢰할 수 있는 서버에서 호출하고 관리자 키를 브라우저에 노출하지 않는다. 서버는 요청의 metadata 객체 전체를 전달하지 말고, 권한 검사 뒤 조회한 프로필 ID로 `app_metadata`를 직접 구성한다. [공식 createUser 안내](https://supabase.com/docs/reference/javascript/auth-admin-createuser)

표식의 값이 UUID라고 해서 비밀 토큰이 되는 것은 아니다. 이 패턴의 보안은 UUID의 추측 난도가 아니라 사용자가 서버 표식을 쓰지 못한다는 경계에 달려 있다. 공개 API로 표식을 복사하거나 수정할 수 있는 다른 경로가 없는지도 확인한다.

## 트리거가 지켜야 할 불변 조건

1. **표식이 없으면 연결하지 않는다.** 표식 없는 가입으로 Auth 행이 생겨도 기존 프로필은 그대로 둔다. 서비스의 데이터 접근은 유효한 프로필 연결과 별도의 활성·권한 검사를 요구해야 한다.
2. **UPDATE에서 표식이 그대로면 연결 처리를 반복하지 않는다.** 사용자가 보조 metadata의 대상 ID를 바꾸거나 unrelated app metadata가 갱신돼도 기존 서버 표식을 재사용해 다른 회원을 연결하면 안 된다.
3. **표식과 보조 대상 ID의 JSON 타입·형식·일치를 검증한다.** 문자열 UUID인지 확인하고, 누락·JSON null·배열·숫자·잘못된 문자열은 유효한 승인으로 처리하지 않는다. UUID 캐스팅 전에 형식을 검사한다.
4. **Auth 계정이 이미 프로필에 연결됐다면 새 연결을 거부한다.** 연결된 계정의 서버 표식을 다른 프로필 ID로 바꿔도 두 번째 프로필을 얻을 수 없어야 한다.
5. **대상 프로필은 미연결 상태여야 한다.** 기존 `auth_user_id`를 덮어쓰는 upsert를 피하고 `WHERE id = target_id AND auth_user_id IS NULL` 조건으로 갱신한다.
6. **서버에서 정규화한 연락처가 일치해야 한다.** 전화번호 기반 명부라면 저장된 정규화 번호와 Auth 번호를 대조한다. 이는 대상 일관성 검사이며, 사용자 제공 연락처만으로 연결을 승인하는 규칙이 아니다.
7. **정확히 한 행이 연결됐는지 확인한다.** 대상 없음·연락처 불일치·이미 연결됨으로 0행이 갱신되면 성공을 반환하지 않는다. `auth_user_id` 고유 제약도 두어 동시 요청의 중복 연결을 막는다.

연결된 상태에서 표식을 없애더라도 자동으로 연결을 해제해서는 안 된다. 이후 같은 표식을 다시 넣거나 다른 표식으로 바꿔도 이미 연결된 Auth ID 검사에 걸려야 한다. 정상적인 metadata 유지보수는 그대로 허용하되, 재연결 기능은 별도의 관리자 절차로 분리한다.

이 설계의 재사용 방지는 **현재 연결 상태**를 기준으로 한다. 별도 관리 경로에서 연결을 해제한 뒤에도 이전 승인을 영구적으로 재사용할 수 없게 해야 한다면, 소비 여부를 보관하는 서버 발급 요청 레코드나 일회성 nonce가 추가로 필요하다. 단순한 프로필 ID 표식을 일회성 비밀로 설명하지 않는다.

## 서버와 프로필 테이블도 같은 경계를 적용한다

프로비저닝 엔드포인트는 JWT의 사용자 신원을 검증한 뒤, DB에서 작업자의 활성 상태와 현재 서비스 권한을 확인한다. 이어서 대상 프로필의 관리자 지위를 조회한다. 일반 회원관리 권한으로 운영진이나 시스템 관리자 계정을 발급·초기화할 수 있으면, 연결 트리거가 안전해도 계정 탈취 경로가 남는다.

프로필 테이블의 INSERT·UPDATE도 역할, 관리자 여부, 인증 연결 ID를 보호해야 한다. 일반 정보 수정용 payload는 보호 필드를 생략하고, 신규 일반 회원은 낮은 권한과 미연결 상태로 생성한다. 권한 승격이나 인증 연결 변경은 시스템 관리자 또는 좁게 제한한 내부 서버 경로에서만 허용한다.

Auth 트리거가 프로필에 쓰기 위해 `SECURITY DEFINER`를 쓴다면 소유자의 권한, 빈 `search_path`, 완전한 스키마 지정, 함수 직접 실행 권한 회수를 함께 검토한다. JWT가 없다는 이유만으로 임의 DB 쓰기를 신뢰하면 안 된다. 트리거 실행 경로와 공개 함수·Data API 경로를 구분해 검증한다.

서버의 성공 응답도 `createUser` 반환값만 보고 결정하지 않는다. 생성된 Auth ID가 의도한 프로필의 연결 ID와 일치하는지 읽거나 조건부 갱신 결과로 확인한다. 후속 단계가 실패하면 이번 요청에서 새로 만든 계정만 정리 대상으로 삼고, 정리 실패도 별도로 추적한다. 기존 계정을 삭제하는 복구 로직을 공용 오류 처리에 넣지 않는다.

## 회귀 검사

실제 Auth 저장 순서를 재현하는 DB 검사와 실제 서버 핸들러 검사를 함께 둔다. 표식이 처음부터 있는 INSERT만 검사하면 운영 발급 오류를 놓친다.

| 시나리오 | 기대 결과 |
| --- | --- |
| 표식 없는 INSERT | Auth 행은 만들어져도 기존 프로필 연결은 변하지 않음 |
| 사용자 metadata에 다른 프로필 ID만 지정 | 연결 안 됨 |
| INSERT 후 유효한 서버 표식 UPDATE | 연락처가 맞는 미연결 프로필 한 개만 연결 |
| INSERT부터 유효한 서버 표식 존재 | 같은 검증 조건으로 연결 |
| 표식 타입·UUID·보조 ID 불일치 | 거부, 프로필 변경 없음 |
| 표식은 그대로이고 사용자 대상 ID만 변경 | 재연결 안 됨 |
| 무관한 app metadata만 변경 | 기존 연결 유지, 연결 처리 반복 없음 |
| 연결된 Auth 계정의 표식을 다른 대상으로 변경 | 거부, 두 번째 연결 없음 |
| 연결된 계정의 표식 제거 후 다시 추가 | 기존 연결 유지, 추가 연결 거부 |
| 이미 연결된 대상 또는 동시 중복 발급 | 덮어쓰기 없이 거부 |
| 일반 회원관리자가 관리자 대상 발급·초기화 | Auth Admin 호출 전에 거부 |
| 계정 생성 후 기대 프로필 연결 없음 | 성공 응답 없음, 신규 계정 복구 절차 수행 |

트리거 로컬 검사가 통과해도 배포된 Auth 버전의 API 순서까지 입증한 것은 아니다. 격리된 검증 환경에서 실제 Admin API 호출도 확인하고, 운영 사용자·인증 토큰·실제 연락처를 문서나 테스트 fixture에 복사하지 않는다.
