# 웹 첫 로딩: 응답 대기와 화면 준비를 나누어 개선하기

확인일: 2026-11-04 · orchestrator: Codex

첫 접속이 느릴 때는 HTML을 받기까지의 대기와 HTML을 받은 뒤 화면이 준비되는 시간을 나누어 본다. 로딩 화면은 사용자가 상황을 이해하도록 돕지만, 지연 원인을 제거하거나 성능 측정을 대신하지는 않는다. 아래 내용은 특정 서비스의 운영 결과가 아닌 범용 점검 원칙이다.

## HTML 이전과 이후의 경계

문서 요청의 TTFB는 탐색 시작부터 응답의 첫 바이트까지의 시간이다. DNS·연결·TLS·서버 대기 등이 포함되므로 전체를 서버의 코드 실행 시간으로 해석하면 안 된다. [web.dev의 TTFB 설명](https://web.dev/articles/ttfb)

새 문서의 HTML을 아직 받지 못한 브라우저는 그 HTML 안의 로딩 화면을 그릴 수 없다. 휴면 중인 서버가 HTML도 제공한다면 페이지 안에 스피너를 추가해도 그 앞의 공백은 남는다. 이 구간은 서버 기동, 연결, 문서 제공 방식 등을 별도로 조사해야 한다.

HTML을 받은 뒤에는 CSS·모듈 다운로드, 스크립트 실행, 초기 API, 렌더링이 이어진다. 첫 안내 문구는 무거운 앱 초기화에 의존하지 않게 문서에 두고, 앱이 준비될 때까지 유지한다. 이 안내 자체가 큰 글꼴이나 그림 다운로드를 기다리게 만들지 않는다.

## cold와 warm을 따로 측정하기

- 서버 휴면 복귀 여부, 브라우저 캐시 상태, 연결 재사용 여부를 각각 기록한다. 이들은 서로 다른 조건이다.
- 첫 요청과 직후 반복 요청을 비교한다. 반복 요청이 빨라졌다는 사실만으로 휴면을 원인으로 확정하지 않는다.
- 실행 시각·환경·표본 수·중앙값·범위를 남기고 서버 기동 로그와 요청 시간을 대조한다.
- 측정 요청이 서버를 깨울 수 있으므로 사전 상태 조회가 cold 조건을 바꾸지 않았는지 확인한다.

플랫폼 기동 시간, 애플리케이션 초기화 시간, 네트워크 왕복을 구분할 수 없다면 구분하지 못했다고 적는다. 로컬 검증 시간 감소를 운영 첫 접속 시간의 같은 비율 감소로 환산하지 않는다.

## 모듈 요청의 발견 지연 줄이기

브라우저가 모듈을 받은 뒤 그 안의 import를 읽어 다음 모듈을 요청하면, 파일 크기가 작아도 의존성 깊이만큼 요청 시작이 늦어질 수 있다. Network 패널에서 요청의 시작 시각과 Initiator를 확인한다.

초기 진입 경로를 번들로 묶으면 일부 요청 경계를 없앨 수 있다. 반대로 큰 단일 번들은 처음에 불필요한 기능까지 내려받고 파싱하게 만들 수 있으므로, 초기 필수 코드와 이후 필요한 코드를 구분한다. 번들 크기와 실제 요청 경로를 함께 비교한다.

작은 수정으로는 필요한 모듈에 `rel="modulepreload"`를 지정해 다운로드 발견을 앞당길 수 있다. 의존 모듈까지 자동으로 가져오는지는 브라우저 최적화에 따라 다르며, 모든 파일을 선행 로드하면 중요한 자원과 대역폭을 경쟁한다. [MDN의 modulepreload 설명](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/modulepreload)

## 로딩 상태와 복구 동작

| 상태 | 사용자에게 제공할 내용 | 전환·검증할 동작 |
| --- | --- | --- |
| loading | 무엇을 불러오는지 짧게 안내 | 실제 앱 준비가 끝나면 화면 표시 |
| slow | 평소보다 오래 걸린다는 안내 | 느린 상태만으로 실패를 확정하지 않음 |
| error | 완료하지 못한 작업과 가능한 다음 행동 | 무한 스피너 대신 재시도 경로 제공 |
| retry | 다시 확인 중임을 안내 | 요청 중 중복 클릭 방지, 오래된 응답 무시 |

실제 진행률을 모르면 임의의 백분율을 표시하지 않는다. 상태 안내는 접근성 알림 영역에서 과도하게 반복하지 않고, 애니메이션을 줄이도록 설정한 사용자도 같은 정보를 얻을 수 있게 한다. 버튼은 키보드로 접근 가능해야 한다.

느린 API뿐 아니라 앱 모듈 자체의 다운로드 실패도 확인한다. 앱 내부에만 오류 처리가 있으면 앱을 불러오지 못했을 때 실행되지 않는다. 재시도 후 이전 요청이 늦게 완료되더라도 새 화면을 덮어쓰지 않도록 요청 식별이나 취소를 설계한다.

읽기 재시도와 상태 변경 재전송은 구분한다. POST의 응답이 시간 초과되었다고 해서 서버가 작업하지 않았다는 뜻은 아니다. 서버의 멱등성 키·처리 결과 조회 등으로 중복 효과를 막을 수 있는 계약이 없다면 자동 재전송을 추가하지 않는다. [RFC 9110의 멱등성·재시도 규칙](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

## 정적 파일 캐시를 바꿀 때

내용 해시가 포함된 URL처럼 내용이 바뀌면 주소도 바뀌는 자산은 긴 유효기간과 `immutable`을 적용하기 쉽다. 배포할 때 같은 URL의 내용을 덮어쓰는 파일에 이를 적용하면 이전 코드가 계속 사용될 수 있다. [MDN의 Cache-Control 설명](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)

고정 URL을 유지한다면 재검증과 버전 갱신 전략을 먼저 정한다. ETag로 본문을 재사용해도 304 확인에는 왕복이 발생한다. HTML과 자산의 배포 순서, 이전 버전 자산의 보존, 새로고침·뒤로가기에서의 호환성도 점검한다.

## 무엇을 측정했는지 정확히 쓰기

| 관측값 | 알 수 있는 것 | 그대로 주장할 수 없는 것 |
| --- | --- | --- |
| curl 응답 시간 | 해당 요청의 연결·응답 대기·전송 시간 | 실제 브라우저 화면 준비 시간 |
| 모듈 개수·전송량 | 요청 구조와 다운로드 부담 | 실제 LCP 개선 폭 |
| 사용자 정의 준비 시점 | 앱이 정의한 초기화 완료 시점 | 사용자가 본 가장 큰 요소의 표시 시점 |
| 브라우저 LCP | 뷰포트 안의 주요 콘텐츠 표시 지표 | 모든 상호작용과 전체 작업의 완료 |

LCP를 측정하지 않았다면 “초기 요청 수 감소”, “해당 API의 응답 시간 감소”처럼 확인한 범위만 보고한다. 브라우저 LCP는 별도 성능 기록이나 적절한 관측 도구로 수집한다. [web.dev의 LCP 정의와 측정 안내](https://web.dev/articles/lcp)

## 비밀정보 없이 측정하기

권한이 있는 공개 읽기 경로부터 시작하고, 인증·쿠키·개인정보가 필요한 경로는 별도 승인과 보관 기준을 따른다. GET이라는 이유만으로 상태 변경이 없다고 가정하지 말고 해당 API의 실제 계약을 확인한다.

Windows에서는 다음 형식으로 본문을 저장하지 않고 요약 시간만 출력할 수 있다. 주소는 측정 권한이 있는 공개 읽기 URL로 바꾼다. 아래 예시는 실행 결과가 아니다.

```powershell
curl.exe --max-time 30 -sS -o NUL -w 'status=%{http_code} dns=%{time_namelookup} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://example.invalid/
```

명령줄에 토큰이나 쿠키를 넣어 이력·로그에 남기지 않는다. HAR·상세 헤더·스크린샷에도 인증값과 개인 응답이 포함될 수 있다. 공유할 결과는 필요한 시간·크기 집계로 제한하고, DNS 실패나 HTTP 오류를 유효한 성능 표본으로 섞지 않는다.
